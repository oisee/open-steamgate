# What 2026-09-18 taught, and what it cost

The day the tree moved to the i7, HANA became a backend, and an ABAP method
whose body is SQLScript started running in a real database without its caller
knowing. Written for the session that comes after, so the lessons are not paid
for twice.

## What landed

- **B.2, the transactional runtime, started.** A composition
  (`@ObjectModel.association.type: [#TO_COMPOSITION_CHILD]`) whose parent
  takes its children with it on delete, and a LUW bracket around a `$batch`
  changeset and around any single modifying request.
- **B.19, HANA.** `STG_DB=hana` is a first-class backend: 148 ABAP unit tests
  and 22 wire tests, the same counts as SQLite.
- **AMDP end to end.** The body is cut out of the class, deployed into HANA
  Express and called; a CDS table function is checked against the method that
  implements it; dates come back in ABAP's spelling. A Z80 CPU written in
  SQLScript executes `LD A,7` inside the database.
- **G.1c.** The screen is "Easy Access" and the picture is rain on a surface.
- Upstream: a measurement comment on #1866, issues #1871 and #1872, PR #1873.

## The one that cost the most: there was no LUW at all

Making a changeset atomic turned up that **nothing in this system had ever
committed**. All three database clients implement `begin`/`commit`/`rollback`,
every write opens a transaction, and nobody ended one — the server ran from
boot to disconnect inside a single open transaction, and the rows survived
only because `export()` and `disconnect()` commit on the way out.

Harmless until something rolls back. A `ROLLBACK WORK` to undo one failed
request would have undone everything since boot, the generation's own tables
included. **The rule: a rollback is always preceded by a commit that fences
it.** Both brackets are written that way.

It also removed a hidden quadratic: `tools/duckdb-client.mjs` emulates
savepoints by replaying the LUW's statements, and while nothing committed that
array grew for the life of the process, so every failed statement replayed the
whole history.

## The mistake made twice in one hour

**A transformation of SQL that distinguishes literals from the rest cannot be
done in two passes.** Parse where the literals are, then run a regular
expression over the whole joined string, and the second step no longer knows
what the first one found.

- Folding identifiers to upper case turned a stored `{"draft":"kept"}` into
  `{"DRAFT":"KEPT"}`, because JSON has double quotes.
- Rewriting `WHERE true` to `WHERE 1 = 1` turned the value `'say true please'`
  into `'say 1 = 1 please'`.

Both were **silent data corruption, not an error**. Both were caught by a test
comparing a stored value — not by reading the code, and not by the build.

## Nine obstacles to a new backend, and eight were not about SQL

Identifier case and quoting; a rerun meeting its own tables; two shapes of
seed insert; the driver's 128 KB packet against megabyte rows in `reposrc`;
two forms of reference in one statement stream; row keys returning upper case;
a double quote inside a JSON value; `hasSchema` asking for its own column in
the wrong case. **One real dialect rewrite**: `WHERE true` → `WHERE 1 = 1`.

That proportion is the useful number. The cost of a backend is in the seam
around the database, not in the database's dialect — which is what the
eleven-method `DatabaseClient` was for.

## Measuring: three times the method was the answer, not the subject

- **"Still downloading" was false for forty minutes.** The check was
  `pgrep -f "docker pull saplabs"`, and the waiting loop's own command line
  contained that string, so it found itself. A process that waits for a
  pattern must not match that pattern. Alice asked "точно качается?" and that
  is the only reason it was caught.
- **`du` lies without permission.** It reported 1 MB for `/var/lib/docker` and
  4.0K for a bind mount owned by another uid, and neither means "empty". Use
  `docker system df`, or measure from inside the container.
- **`--top 0` is documented as "all" and returns exactly 100.** The first AMDP
  corpus answer — "100 classes, none of them customer" — was wrong in both
  halves. The real number is 195 and three are ours. The only clue was that
  100 is a round number; Alice spotted it.

## What the critic changed, twice

Both times the decision survived and the **reasoning** did not.

- Parking the perf branch was right, but "a few percent at whole-program
  level" was not supportable: the column it rested on measured a placement
  that was never shipped, and its numbers were inside the noise. The
  defensible claim is "below our measurement threshold".
- The wrapper-versus-temp-table comparison: my explanation ("parse cost grows
  faster than the saving") was contradicted by my own per-row numbers, which
  were flat. The real finding was structural — a statement carrying its values
  in its text is new text every time and can never hit the plan cache. Running
  the same 2000-branch statement twice showed 2478 ms then 4 ms: **99.8 % of
  it is parse.** That pointed at the fourth method nobody had measured, bound
  parameters, which is 369x faster at 10 000 rows and removes the whole class
  of escaping defects above.

## Small rules worth keeping

- A generator reads **content** (`src`, packs), never the whole input-folder
  list — it picked up a test fixture, which CLAUDE.md already records happening
  once with a CDS fixture. A fixture that looks like an object must not be
  named like one: they are `*.abap.txt` now and `test/fixtures/` is in
  `exclude_filter`.
- Commit by naming files, not with `git add -A <dir>`: a wide add swept six
  files belonging to another session into a commit. Amending it back out kept
  every byte, but the near-miss was real.
- `npm run leak` with no arguments says "nothing was read — that is not
  clean", and it is right to. The push hook reads the tracked set and that is
  the one that matters.

## Two things a critic found in our own numbers, before anyone outside did

Both were caught reading an upstream draft against the repository, and neither
is about the draft: they are about how we hold numbers.

**A number with two owners drifts.** `docs/db-backends.md` said 146 unit tests
and `docs/retro-2026-09-18.md` said 148, written the same day, six hours apart,
about the same suite. Neither was wrong at the moment it was written -- two of
the tests begin `IF sy-dbsys <> 'HDB'. RETURN. ENDIF.`, so the suite really is
146 on sqlite and 148 on HANA. What was wrong was that the number lived in two
places with no statement of which. The fix is the one we already applied to the
corpus: **a number has one owner**, everything else links to it, and if a
second document needs it the link goes in, not the digits.

**Quoting one number out of a range is choosing the convenient one.** A draft
said HANA is "52x slower on a single-row SELECT", which is measured and true.
The measurement is a three-row table: 52x on a single-row SELECT, **146x** on a
single-row INSERT, and **3.8x** on a 200-row SELECT. The shape is the finding --
the cost is per statement, not per row -- and quoting the middle number hides
both the worse case and the reassuring one. Rule: **the range goes in whole, or
it does not go in.**

The general form, and it is the same as the false-green rule: a fact that
flatters us gets less scrutiny than one that does not, so it needs more.
